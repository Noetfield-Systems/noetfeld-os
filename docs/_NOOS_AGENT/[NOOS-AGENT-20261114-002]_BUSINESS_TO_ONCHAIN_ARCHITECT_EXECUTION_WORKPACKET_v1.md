## 0. Executive mandate and non-negotiable product outcome
Users should be able to say: "I have a startup/company/business model; I want to operate internationally, bring AI and/or Web3 into it, use cryptocurrency or bank money, choose an entity strategy, find suitable specialists and get launched." The Architect responds with **a usable, evidence-linked plan and real next action**, not an encyclopedia or generic prompt text.
The OS does not have to own every specialized service. Instead assemble one or several companies, professionals, autonomous agents, PSPs and protocols into an inspectable Economic Route with explicit roles, milestones, costs, custody/settlement ownership and verification.
The default product NEVER insists on a token, company registration, blockchain contract or full AI automation if a conventional or hybrid path wins for that specific goal.
No artificial "consult lawyer first" dead-end. Missing entity/financial permissions only gate the affected execution node; product discovery, plan generation, referrals, business setup, developers, proposals, demos and unrelated paid services remain operational.
No invented completed actions or partner relationships. Keep relevant existing venture boundaries. Reuse RWA Clinic, Control Sandbox, existing /onchain/ Hub, Company OS, intake/CRM, verification and payments when functioning. Do not replace GEL's older locked product SSOT. This is a separately owned ecosystem product interface and cross-repo contract.

## 4. Architect engine: deterministic backbone + AI explanations
Pipeline:
INPUT_CAPTURE -> NORMALIZE -> INTENT_CLASSIFY -> FACTS/UNKNOWN_RECONCILE -> OPERATING_MODEL_COMPARE -> JURISDICTION_COMPARE -> CAPABILITY_DAG -> PROVIDER_SEARCH -> MULTI_ROUTE_COMPOSE -> COST/TIME_ESTIMATE -> REVIEW/ACCEPT -> ENGAGEMENT -> EXECUTION/SETTLEMENT -> VERIFICATION.
The default numeric and dependency assessment is deterministic, versioned and testable. An LLM may extract user intent and explain scenarios, but must not fabricate official rule values, legal judgments, actual providers, project finances, quotes or completed actions.
Rule engine:
- Rule record: rule_id, territory, business_activity, entity_type, fact_predicate, relevant_date, valid_from/to, source_url, last_verified, owner, confidence, impact, decision, review_trigger.
- Structured facts: evidence_status = VERIFIED / USER_ASSERTED / INFERRED / UNKNOWN; do not silently elevate inferred to verified.
- Comparisons: hard impossible constraint flags (e.g. unsupported provider capability) and soft weighted suitability; a restricted action is treated as "needs specialized executing party" if a route can proceed.
- Output: rationale and confidence per option, uncertainty list, fact-request list and list of actual service providers in each route.
- Recommendation: prefer lowest **total cost, delivery time and operational friction** that achieves the requested value. No Web3 maximalism.
- Avoid false precision: use ranges and confidence, not invented fixed corporate setup prices/tax savings or guaranteed capital returns.
- If model can't evaluate a target jurisdiction, return "needs sourced review / partner quote" and preserve the project, onboarding and remaining workflows.

Baseline scoring per model (normalized 0..100): business/outcome fit 0.25; operational feasibility 0.20; capital & payment fit 0.14; jurisdiction fit 0.14; delivery capacity 0.12; total cost fit 0.10; user preference 0.05. Hard requirements filtered first; explanations show each component; do not weight country tax more than actual user objective.
Provider composition score **inherits parent architecture**: capability .24, deliverability .18, jurisdiction .16, total cost .14, verified outcomes .12, completion time .10, user preference .06; select top 3 **distinct viable compositions**, not 3 aliases for one provider. Use explicit candidate status. If registry empty, show "provider needed" with open-call posting and team recruitment CTA; do not invent candidates.
